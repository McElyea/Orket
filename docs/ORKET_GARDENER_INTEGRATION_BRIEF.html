Local maintenance agents

Responsibilities and contract

One execution owner. Explicit inputs and results.

Gardener submits

  • Repository identity and exact revision, plus a bounded snapshot reference.
  • Conventions reference and revision; one report-only audit intent.
  • A stable request ID and requested time, model, and token limits.
  • Caller identity through an authenticated transport.

Orket returns

  • Accepted job/run identity and inspectable execution status.
  • Findings linked to source paths and the audited revision.
  • Resolved model identity, usage, latency, and verification evidence.
  • Coverage limits, incomplete work, and decisions still required.

Orket enforces: allowed inputs, host policy, effective budgets, cancellation, recovery, and result acceptance. Requested limits cannot expand host permissions.

The extension proposes: findings and, in later phases, changes. Host services authorize and execute admitted effects.

Prevent duplicate work: Gardener selects repositories and requests jobs. Orket owns execution retries and leases. Repeated submissions with the same identity resolve to the same job; conflicting payloads must be rejected. The pilot uses manual submission only.

Conceptual fields only; the first implementation should reuse canonical Orket contracts.04 / 08

First vertical slice

One repository. One local model. A useful audit.

1

Freeze the input and expected checks

Select a small repository at an exact commit and a pinned conventions set. Include known gaps and compliant examples for review.

2

Build the smallest Orket maintenance extension

Provide bounded snapshot context, request host-brokered local inference, and return structured findings with source references.

3

Connect a single Gardener audit request

Add a narrow dispatch path that submits the job, retrieves its status, and displays the result. Reuse Orket’s run lifecycle services.

4

Run the real path and inspect evidence

Exercise normal completion, duplicate submission, unavailable model, and cancellation. Inspect actual repository state and recorded outcomes.

Pilot boundary: read-only target snapshot; report artifacts may be written. No source edits, issue posting, PR creation, merges, skill bootstrap, or unattended fleet execution. No automatic cloud fallback.

An audit report is model-assisted advice. File references and execution receipts substantiate its inputs and path; human review determines whether each finding is correct.

All pilot actions and checks are proposed; none has been run for this integration.05 / 08

Proposed sequence and discussion

Make the next commitment small.

PHASE 1 / PROVE

Report-only audit

Deliver the bounded job path, a focused extension, and live evidence. Decide whether local-model quality and the integration justify further work.

PHASE 2 / EXTEND

One repair and test

After accepting Phase 1, admit one scoped edit and test workflow. Add required capabilities, approval behavior, recovery, and independent result verification.

PHASE 3 / OPERATE

Fleet maintenance

After proving repair behavior, establish scheduling ownership, repository exclusion, capacity limits, and interrupted-work recovery across repositories.

Evidence and limits · reference slide

What exists, and what remains to be proven.

Existing foundations

Gardener dispatches Claude Code for audits and development loops. Orket’s inspected workspace has a governed agent SDK/broker, local Ollama execution, and durable run controls.

Orket’s current authority records prior bounded local-model proof. That proof was not rerun for this proposal.

Proposed work and constraints

The maintenance-job contract, Gardener backend, and maintenance extension are new work. Broader repository repair/test/Git capabilities need admission and proof.

Gardener’s current Unix dependencies favor Linux/WSL for a pilot. Repository branch, CI, and release rules must be reconciled before write workflows.
